# Модель Выполнения

Сценарий выполняется императивно: инструкция за инструкцией, сверху вниз.

Результат выполнения сценария - список обычных `LOAD`-таблиц, которые остались в контексте после выполнения и очистки временных таблиц.

## Контекст Выполнения

Во время выполнения `ScriptContext` хранит:

- целевое подключение к ClickHouse/DWH;
- основной `FileStorage` для файловых провайдеров;
- реестр подключений для `Connect`;
- список уже загруженных script-таблиц;
- префиксы физических temp/final таблиц;
- logger/progress events.

## Pipeline LOAD

Каждый `LOAD` проходит несколько этапов.

```text
Разрешить FROM
-> Подготовить источник
-> Подготовить трансформации
-> Скомпилировать ClickHouse SQL
-> Материализовать финальную таблицу
-> Зарегистрировать LoadedTable
```

## Разрешение FROM

Resolver разбирает источник из `FROM`.

Источник может быть двух видов:

- reader-source: внешний reader, например `Csv`, `Json`, `Excel`, `Qvd`, `Xml`, `Inline`, `Numbers`, `Connect: БД`, `Connect: Папка`;
- DWH-source: данные уже находятся в целевом DWH и доступны ClickHouse напрямую, например `Table`, `Union`, `Join`, `Calendar`, `Connect: Файл`.

## Подготовка Источника

Reader-source сначала физически загружается во временную ClickHouse-таблицу. После этого `LOAD` работает уже поверх этой временной таблицы.

DWH-source не требует отдельной временной таблицы перед query: он передается дальше как SQL-фрагмент.

Подключение к внешней БД не является DWH-source, даже если внутри написан SQL. Такой `Connect` открывает reader внешней БД и дальше проходит путь reader-source.

`FIRST N` применяется к исходным строкам source до вычислений `LOAD`.

## Подготовка Трансформаций

Поля source превращаются в типизированный query context.

`LOAD`-выражения, `WHERE`, `GROUP BY`, `ORDER BY`, `LIMIT`, `OFFSET` резолвятся в одну ClickHouse query.

Если написан `LOAD *`, явный список select-полей не создается: выбираются поля source.

Не каждый `FROM` поддерживает все формы трансформаций прямо в той же инструкции. Например подключение к БД использует `SQL` после `FROM Connect(...)`, а `Inline` запрещает `WHERE`, `GROUP BY`, `ORDER BY`, `LIMIT` и `OFFSET` в той же инструкции. Такие случаи описаны в документации конкретного провайдера.

## Материализация Финальной Таблицы

Результат query всегда сохраняется в физическую финальную таблицу в ClickHouse.

Физические имена генерируются автоматически через префиксы из `ScriptContextOptions`.

После успешной записи создается `LoadedTable`:

- `Alias` - имя script-таблицы из сценария;
- `Name` - физическое имя ClickHouse-таблицы;
- `Kind` - `Normal`, `Temp` или `Mapped`;
- `Fields` - логические имена и доменные типы результата;
- `RowCount` - количество записей в финальной таблице.

## Что Является Финальным

Обычный `LOAD` создает финальную таблицу, которая возвращается вызывающему коду после выполнения сценария.

`TEMP LOAD` тоже материализуется в ClickHouse и доступен следующим инструкциям, но не возвращается как результат сценария и очищается после выполнения.

`MAPPED LOAD` создает служебную mapping table для lookup-функций. Она доступна следующим инструкциям, но очищается как временная таблица.

## Очистка

После успешного выполнения всех инструкций executor удаляет `TEMP` и `MAPPED` таблицы.

Если сценарий падает с ошибкой, executor делает best-effort очистку временных таблиц. Исходная ошибка сценария важнее ошибки очистки.

`DROP` удаляет таблицу сразу и убирает ее из контекста сценария.

## Ошибки

Ошибки имеют этап:

- разрешение провайдера;
- запись временной таблицы;
- разрешение query;
- компиляция query в ClickHouse SQL;
- запись финальной таблицы;
- удаление таблицы.

Если ошибка произошла внутри инструкции, она оборачивается в `LoadScriptException` с индексом инструкции.
